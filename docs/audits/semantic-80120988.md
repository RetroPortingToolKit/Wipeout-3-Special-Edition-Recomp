# Semantic audit: `0x80120988` / `CopyAndNormalizeControllerPacket`

## Result

`0x80120988` is the raw controller-response copier and sanitizer now named
`CopyAndNormalizeControllerPacket`:

```c
void CopyAndNormalizeControllerPacket(uint8_t *destination,
                                      const uint8_t *source);
```

It copies eight response bytes (or clears them when the source is null), saves
the raw two-byte header separately, and substitutes neutral controls whenever
the response header is not one of the supported controller IDs.

## Exact owner and ABI

The complete owner is `[0x80120988,0x80120A88)`, exactly `0x100` bytes,
matching the generated range table. It is frameless and calls no subroutine.
The preceding critical-section helper returns at `0x80120980` with its delay
slot at `0x80120984`; the next independent owner creates a frame at
`0x80120A88`.

`a0` is the destination packet and `a1` is an optional eight-byte source. No
meaningful scalar result is established: exits retain compare/constants in
`v0`, and all callers ignore it. The semantic return is void.

Every retained caller supplies a nonzero destination. The initial
`beqz a0,0x80120A1C` skips copying/clearing but the later code still accesses
guest address zero; it is not a C-style null-success path and does not provide
a safe null-destination contract.

## Copy, snapshot, and validation

For an ordinary destination, the first phase is exact:

```c
if (source != NULL)
    copy destination[0..7] = source[0..7];
else
    clear destination[0..7] = 0;

uint16_t raw_header = load_le16(destination + 0);
store_le16(destination + 8, raw_header);
```

The header snapshot at `+8` always precedes normalization, preserving the
original response/type/status pair for later consumers.

These little-endian header words are accepted unchanged:

```text
0x2300  controller ID 0x23 with status byte 0x00
0x4100  controller ID 0x41 with status byte 0x00
0x7300  controller ID 0x73 with status byte 0x00
```

For any other header, the function writes the neutral fallback:

```text
destination +2..+3 = 0xFFFF   all active-low buttons released
destination +4     = 0x80     centered axis
destination +5     = 0x80
destination +6     = 0x80
destination +7     = 0x80
```

Finally, invalid headers `0x23FF`, `0x41FF`, and `0x73FF` are recognized as
error/status variants of supported IDs and destination `+0..+1` is rewritten
to canonical digital header `0x4100`. Other invalid headers retain their raw
first two bytes while receiving the same neutral buttons and axes. In every
case `+8` retains the pre-normalization header.

The function writes only destination bytes `0..9`; it changes no global,
queue, callback, controller hardware, or interrupt state.

## Complete caller and interior-target census

An exhaustive aligned instruction-word scan of the retained executable finds
exactly seven direct calls:

```text
801167CC
80122B6C 80122BB8 80122D84 80122DD0
80123544 80123590
```

All seven target `0x80120988`. The direct jump at `0x801209B4` to
`0x80120A1C` is internal, leaving the completed null-source zero-fill path and
skipping the alternative byte-copy path. No external `j` or `jal` targets any
interior address, including that normalization block.

The single stack-local caller obtains a raw response from `0x801203F0`,
normalizes it into a ten-byte local packet, and immediately tests the same
three supported header words. The six session-update calls address controller
packet fields inside 0x3A4-byte racer records; paired paths first clear them
with a null source, then copy a live response when available. None consumes
`v0`.

## Defensible identity

The `0x41` and `0x73` IDs, active-low `0xFFFF` button fallback, four `0x80`
axis centers, copy-from-pad-response caller flow, and original-header snapshot
together establish a controller packet normalizer rather than a generic
ten-byte copy. The name avoids assigning a narrower controller-model identity
to ID `0x23`, whose exact peripheral mapping is not needed for this behavior.
