# Semantic audit: generated boundaries `0x80172940` and `0x801731D4`

## Conclusion

Neither generated range is a source-level ABI function. Both are control-flow
fragments split out of already cataloged renderer routines:

- `0x80172940` is `SubdivideMeshProjectedVertexClipLoopTail`, an internal and
  shared continuation of `SubdivideAndSubmitMeshPrimitives` at `0x801727E8`.
- `0x801731D4` is `VisibleQuadListOverflowReturn`, the overflow-only return
  epilogue of `BuildVisibleOrientedQuadList` at `0x80172E3C`.

They are therefore recorded as `[[block]]` entries rather than `[[func]]`
entries. The generated splitting remains useful to the recompiler and does not
need to be changed to correct the semantic catalog.

## `0x80172940`: projected-vertex clip-loop tail

The preceding emitted piece falls through directly from `0x8017293C` to
`0x80172940`. It has just stored one projected midpoint's SXY and depth-derived
value. The split piece loads the projected X/Y halfwords at `work-8` and
`work-6`, computes their four screen outcode bits using the live width and
height registers, ANDs that outcode into the running aggregate, and stores it
at `work-2`.

The branch at `0x80172974` proves that this is a loop continuation rather than
a callable entry: when the live remaining-vertex counter is positive it jumps
back to `0x80172840`; otherwise it clears `k1` and jumps to the shared renderer
continuation at `0x80171D04`. It has no prologue, frame construction, argument
capture, independent return, or stable entry-state contract.

Three captured low-RAM overlay variants also jump from `0x800D2080` to
`0x80172940`. Those are tail-entries into the resident routine's shared
continuation, not ABI calls: their preceding instructions prepare the same
live work record and outcode state, and the jump does not set `ra`. This
cross-overlay reuse explains why the recompiler must retain a separately
dispatchable range even though the semantic boundary is only a block.

## `0x801731D4`: visible-list overflow return

Inside `BuildVisibleOrientedQuadList`, the accepted-record capacity branch
targets `0x801731D4`. The fragment sets `v0 = -1`, reconstructs the scratchpad
save-frame address `0x1F8003D4`, restores exactly the register set saved by the
owner (`ra`, `fp`, `s0-s7`, and `gp`), and returns through the restored `ra`.
It does not create a frame or accept arguments.

The owner's normal path immediately before it performs the same restoration
at `0x801731A4..0x801731D0`, but returns the accepted count instead. No other
base-image branch, `jal`, function-pointer reference, or captured overlay edge
targets `0x801731D4`. The separate 60-byte generated range is consequently an
overflow epilogue split for control-flow/code-generation purposes, not an
independent function.

## Primary evidence

- `generated/SCES_028.45_full_139.c`: contiguous fallthrough into
  `0x80172940`, its loop/backedge and tail transfer, the capacity branch into
  `0x801731D4`, and both normal/overflow restore sequences.
- `generated/SCES_028.45_full_03.c`: three low-RAM overlay tail jumps into
  resident block `0x80172940` without link semantics.
- `generated/SCES_028.45_dispatch.c`: generated range/dispatch boundaries;
  these establish recompiler entry requirements but not source-level ABI
  functions.
- `docs/audits/semantic-801727ec.md` and
  `docs/audits/semantic-80172e3c.md`: audited owner boundaries and behavior.
