# Semantic audit: `0x80161338` / `CdDataCallback`

## Result and ABI

`0x80161338` is the canonical LibCD data/DMA callback wrapper:

```c
typedef void (*CdDataCB)(void);
CdDataCB CdDataCallback(CdDataCB callback);
```

It forwards the incoming callback to the shared DMA-callback dispatcher with
fixed DMA channel `3`, the PlayStation CD-ROM DMA channel, and propagates the
dispatcher result (the previously installed callback) unchanged.

## Exact boundary and target census

The generated range assigns `[0x80161338, 0x8016135C)`, exactly `0x24` bytes,
to this owner.  It opens a 24-byte frame, saves only `ra`, calls the dispatcher,
restores its frame, returns at `0x80161354`, and executes a NOP return delay
slot at `0x80161358`.  The next independent owner begins at `0x8016135C`.

An aligned scan of the authenticated executable finds exactly nine direct JAL
sites:

```text
801605B0 801605D0 80160758 8016083C 801608CC
80160A28 80160BAC 80163CB4 80163D48
```

There are no calls to an interior instruction.  The wrapper's only outgoing
call is `0x801625EC` at `0x80161344`.

## Forwarding and callback state

The machine-level formula is:

```c
CdDataCB CdDataCallback(CdDataCB callback) {
    return DMACallback(3, callback);
}
```

Incoming `a0` is moved to `a1`; constant `3` is installed in `a0` in the JAL
delay slot.  No instruction after the call changes `v0`.  The dynamic helper
at `0x801625EC` loads the active DMA service table through global
`0x8017A4EC`, calls its callback-exchange method at table offset `+4`, and
returns that method's result.  Thus actual callback storage is owned by the
selected DMA backend rather than a fixed LibCD global in this wrapper.

Passing null removes/suppresses the channel-3 callback according to the DMA
backend; passing a function installs it and returns the displaced function.
The wrapper performs no pointer validation, locking, interrupt masking, or
direct DMA register access.  Unlike `CdReadyCallback` and `CdSyncCallback`, it
does not touch `0x8017B128` or `0x8017B124`.

## Caller roles

The nine sites install, clear, and restore the callback around LibCD sector
transfer and lifecycle operations.  Concrete callback `0x801607BC` advances a
stream transfer pointer/count when data arrives, while other paths pass null
or saved callbacks during shutdown/reconfiguration.  Several callers exchange
data, ready, and sync callbacks together, but the data callback is specifically
routed through DMA channel 3.

No caller supplies or expects event arguments for the observed data callback;
the installed handler is invoked for transfer completion and reads its state
from LibCD globals.  The return is used as a callback pointer where save/restore
is required, not as a boolean status.

## Confidence

`confirmed`: canonical identity, exact boundary and callback ABI, fixed CD-ROM
DMA channel, exhaustive caller/interior-target census, dynamic backend route,
old-callback return propagation, concrete transfer callback role, and absence
of direct persistent/hardware effects are instruction-proven.
