# Semantic audit: `0x80141458` / `QueueOrientedQuadSourceRecord`

## Result and ABI

`0x80141458` appends one 28-byte source record to the scene-oriented-quad
queue consumed by `BuildVisibleObjectQuadPackets`, and is now named
`QueueOrientedQuadSourceRecord`:

```c
void QueueOrientedQuadSourceRecord(
    const int32_t position[3],
    uint16_t field_c, uint16_t field_e, uint16_t flags,
    int16_t field_12, uint8_t field_14,
    const uint8_t bytes_15_17[3]);
```

The first four arguments occupy `a0..a3`; the last three are incoming stack
arguments at `+0x10`, `+0x14`, and `+0x18`. No semantic result is returned.

## Exact owner and admission

The exact generated owner is `[0x80141458,0x801415F4)`, length `0x19C`. It
uses an eight-byte leaf frame only to preserve `s0`, performs no calls, and
returns at `0x801415EC` with frame restoration in the delay slot. The next
independent owner begins at `0x801415F4`.

If mode byte `0x801D1B3E` equals one, the routine returns without mutation.
Otherwise it uses halfword indices at `0x801762C8` and `0x801762CA` and the
28-byte record array at `*(void **)0x801E247C`. While the tail record has flag
bit `0x0002` set, it advances the tail, but stops and drops the new record when
`tail - head` reaches 64. It also drops the append directly when the current
window is already 64 entries. There is no pointer validation.

## Exact record writes

At the accepted tail slot it writes:

```text
+0x00..+0x08  three position words copied from a0
+0x0C         low 16 bits of a1
+0x0E         low 16 bits of a2
+0x10         (low 16 bits of a3) | 0x8000
+0x12         signed halfword from stack +0x10
+0x14         byte from stack +0x14
+0x15..+0x17  three bytes copied from *(stack +0x18)
```

It then increments the tail halfword at `0x801762CA`. The forced `0x8000` bit
marks the record active for the downstream visible-object pass; bit `0x0002`
is the skip/consumed condition used while finding the next writable tail.
Fields not listed (`+0x0A`, `+0x18..+0x1B`) are not written here.

## Callers, targets, and overlay accounting

Exactly five executable calls target the true entry:

```text
80126B60 80126B80 80156064 801561C4 80156280
```

They supply world/screen-oriented positions, size/angle-style halfwords, a
small attribute byte, and a three-byte color/material tuple. The paired calls
at `0x80126B60/0x80126B80` enqueue two related records; the remaining three
are alternate producers in another scene/effect owner.

No external direct jump or JAL targets any interior instruction. An exact-body
scan finds only `0x80141458`, so overlay overlap produces no duplicate logical
owner or caller. The next routine's independent audit proves that these same
28-byte records are compacted for visibility and emitted as textured quads,
supporting the deliberately producer-focused name.
