# Semantic audit: `0x80110094` / `DrawAsciiFontCharacter`

## Result

`0x80110094` is the ASCII-to-font adapter now named
`DrawAsciiFontCharacter`:

```c
int DrawAsciiFontCharacter(uint8_t character, int x, int y, int style);
```

It handles NUL and space locally, maps the supported printable ASCII subset to
the game's glyph numbering, emits one glyph otherwise, and returns horizontal
advance rather than the final X coordinate.

## Exact logical owner and generated aliases

The complete function is `[0x80110094,0x80110198)`, exactly `0x104` bytes. It
opens a `0x18`-byte frame, converges all paths at one subtraction/epilogue,
returns at `0x80110190`, and restores the stack in the delay slot at
`0x80110194`. The adjacent `LoadQuadTextureCoordinates` begins at
`0x80110198`.

Generated range metadata repeats this same `0x104`-byte owner under 14 labels
from `0x801100E8` through `0x80110150`. They are the destinations of the
function's computed punctuation jump table and are emitted as alias entries so
the recompiler can dispatch the indirect `jr`. They are neither separate
semantic functions nor external interior callers.

`a0` is explicitly narrowed to a byte. `a1` is retained as a signed-halfword
baseline for the final subtraction, while its full value is forwarded as the
glyph X coordinate. `a2` and `a3` pass through as Y and font style. The return
is the emitted/space advance `new_x - (int16_t)x`; authored frontend callers
add it to their current pen.

## Character mapping and behavior

The exact special cases are:

```text
NUL          no draw, advance 0
space        no draw, advance 8
'A'..'Z'     glyph 0x00..0x19
'0'..'9'     glyph 0x1A..0x23
':' '.' '/'  glyph 0x24 0x25 0x26
'+' '-' '%'  glyph 0x27 0x28 0x29
'#' '^'      glyph 0x2A 0x2B
'[' ']' '_'  glyph 0x2E 0x2F 0x30
'=' '?'      glyph 0x31 0x32
```

For a drawable character it calls:

```c
new_x = EmitFontGlyphPacket(glyph, x, y, style);
return new_x - (int16_t)x;
```

Other punctuation below `'0'` follows the initialized glyph-zero fallback.
The generic path mechanically subtracts `'A'` from byte values at or above
`'A'`, so lowercase and higher bytes can produce glyph IDs beyond the proven
authored set; there is no validation here. Callers normally supply translated
uppercase frontend text. The name therefore describes the adapter's encoding,
not a claim of complete ASCII coverage.

The only externally visible render state is that of confirmed
`EmitFontGlyphPacket`: allocation and OT-linkage of one `POLY_FT4`. NUL and
space do not allocate or mutate render state.

## Unique callers, duplicated translations, and interior targets

The retained main executable contains exactly three entry calls:

```text
801008FC  801009E4  801009FC
```

The static overlay corpus contains three additional unique guest call PCs:

```text
800D501C  800D5034  800D5120
```

Each overlay call PC is translated four times for four overlay images. With
the three main-EXE calls, generated output therefore contains 15 call
emissions but only six unique runtime instruction addresses. The repeated
translations do not establish additional semantic callers.

The main frontend owner uses the helper in a translated string loop, adding
the returned advance to its X pen, and in special-character paths. No external
J or JAL targets an interior address. All interior direct jumps shown by the
raw scan are this owner's punctuation cases converging at `0x80110170` or its
common return path. Its sole outgoing call is `EmitFontGlyphPacket` at
`0x80110170`.
