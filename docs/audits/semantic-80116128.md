# Semantic audit: `0x80116128`

## Result

Recommended symbol: `RunRaceSession` (`known`).

This is a true callable boundary, not an internal label. It owns the generated
range `0x80116128..0x8011675F` (1,592 bytes). The entry allocates a 256-byte
stack frame and saves `ra`, `fp`, and `s0..s7`. The next range at `0x80116760`
starts another conventional stack frame, independently confirming the end.

The routine is effectively `void RunRaceSession(void)` and does not return in
the retained control-flow graph. No incoming argument register is consumed as
an input before being overwritten. Its only direct caller is the startup path:
the `jal` at `0x80162510` calls `0x80116128`, and the nominal return site at
`0x80162518` is a `break 1` trap. There are no other direct `jal` sites to the
entry in the complete generated image.

## Game-loop role

The entry first performs one-time subsystem and race-state setup. Evidence in
the instruction stream includes repeated initialization calls, construction of
local display rectangles, installation of five adjacent callback/state slots,
initialization of global race/view records, and setup calls before the first
frame path. The exact semantics of every setup callee remain unresolved, so
the symbol deliberately names the owned session rather than overclaiming a
specific menu or simulation API.

After setup, control enters a closed frame loop. The central path beginning at
`0x8011651C` prepares the active player/view state. At `0x80116590` it loads:

- `a0` from the active race/player record at global `0x801D1B7C`;
- `a1` from the render-context global at `0x801D1B80`;
- `a2` from the routine's stack-local context at `sp+0xD4`.

The `jal` at `0x801165A0` then calls `RenderRaceFrame` (`0x8012268C`). This is
the only direct call to that renderer in the retained executable. Post-render
logic selects one of several view/player update paths, updates per-view state,
and converges at `0x80116728`. The back edge at `0x80116738` returns to
`0x80116590`; another mode path at `0x80116758` returns to `0x8011651C`.
Neither path reaches an epilogue or restores the saved return address.

This establishes `0x80116128` as the race-session owner and persistent game
loop rather than merely a frame renderer. `RunRaceSession` is therefore more
precise than `MainLoop`: startup and race initialization are part of the same
non-returning function, while `RenderRaceFrame` remains the subordinate
per-frame rendering routine.

## Confidence limits

The boundary, sole caller, lack of ABI arguments, non-returning behavior, and
ownership of the render call are directly established. `known` is appropriate
because the proposed source-level name is semantic rather than recovered from
original debug data, and the individual setup/update callees have not all been
named.
