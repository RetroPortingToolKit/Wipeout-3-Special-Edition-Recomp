# Tail-boundary audit: `0x8017B920` and `0x8017BBA4`

## Result

Neither generated entry is an ABI-callable function. Both are ordinary
straight-line instructions inside the single function
`UpdatePerformanceTuningMenu`, whose exact extent is
`0x8017B90C..0x8017BBCF` (`0x2C4` bytes):

- `0x8017B920` completes `s0 = 0x8017B8E4`, the address of the menu's private
  state object;
- `0x8017BBA4` converts the selected frame-rate mode to the PAL-x2 boolean
  written four instructions later.

They are cataloged as internal blocks/sites so their misleading generated
`func_` identities are not promoted into the semantic ABI.

## True code owner and boundaries

`0x8017B90C` has an independent 32-byte o32 frame prologue and saves `ra`,
`s0`, and `s1`. Control then falls linearly through `0x8017B920`; no branch,
call, return, or alternate state enters there. All later branches remain inside
the same frame. The common tail is:

```text
8017BBB8  lw    ra,0x1c(sp)
8017BBBC  lw    s0,0x18(sp)
8017BBC0  lw    s1,0x14(sp)
8017BBC4  addiu sp,sp,0x20
8017BBC8  jr    ra
8017BBCC  nop
```

The next bytes at `0x8017BBD0` are zero padding, not fallthrough code. The
menu tables begin at `0x8017BC18`. Conversely, the `0x28` bytes immediately
before the prologue, `0x8017B8E4..0x8017B90B`, are mutable menu state rather
than instructions. This establishes the code/data split independently of the
generator's many tiny tail ranges.

There is exactly one real direct call to the owner: `0x80123EF8`, inside
`RenderRaceFrame`. No executable call or stored function pointer targets either
interior address.

## Why the generated entries are false

The two apparent direct JAL encodings occur at `0x800D2654` and `0x800D269C`.
Those addresses are not live instructions. They lie in the loader's
`0x1DC`-entry destination/value relocation-pair table beginning at
`0x800D24A8`, after the `0x7BC`-word high-RAM source image. Interpreting the
table values as MIPS happens to produce:

```text
800D2654  0x0C05EE48  apparent jal 0x8017B920
800D269C  0x0C05EEE9  apparent jal 0x8017BBA4
```

The startup loader consumes these words as data while relocating its
`0x80780000` image. The whole-executable scanner followed the accidental bit
patterns and split the genuine tail function at their targets. This also
explains the dense run of implausible 4/8/12-byte generated `F` entries around
`0x8017B920..0x8017BBC4`.

## Recovered owner role

The owner aggregates controller fields `+0x2A` and `+0x2E` across at most 16
records of stride `0x3A4`. A button chord toggles the menu. While open, the
remaining bits select one of four rows and decrement/increment its option,
with per-row limits `{3,10,4,3}`.

The data at `0x8017BC18` supplies four patch-descriptor tables, option tables,
and the literal row labels `FRAME RATE`, `SHIP LOD`, `SHIP DIST`, and `BIRDS`.
Changed non-frame-rate selections copy halfwords through those descriptors;
the owner then calls `0x80168D18`. When visible, it draws the four labels,
selected options, and `>` marker through `0x80105B78`, then calls
`0x8012BA1C`.

Finally, selector `n = *(uint32_t *)0x8017B8EC` is published as:

```c
gSimVblankSkip = (n < 1) + 1;  /* selector 0 -> 2; otherwise 1 */
gPalX2TitleState = (n >= 2);    /* selector 2 -> 1 */
```

At `0x8017BBA4`, `xori t4,t4,1` is therefore only the second half of the
`n >= 2` calculation begun by `sltiu t4,t5,2` at `0x8017BBA0`; calling it in
isolation would consume arbitrary register state and is not meaningful.

## Catalog decisions

- `0x8017B90C`: confirmed function `UpdatePerformanceTuningMenu`, `emit=false`.
- `0x8017B920`: confirmed internal block/site
  `UpdatePerformanceTuningMenuStateBase`.
- `0x8017BBA4`: confirmed internal block/site `PublishPalX2SelectionFlag`.
- `0x8017B8E4`: confirmed `gPerformanceTuningMenuState` data object.
- `0x8017BC18`: confirmed `kPerformanceTuningMenuTables` data region.
- `0x80175064`: confirmed `gPalX2TitleState` object.
